Forms & notifications

Pipes v2 · companion to the main design handoff

The pieces v1 didn’t cover: form states (error, summary, async availability) and in-app notifications (toasts, undo, inline banners). Same system — tokens from pipes.css, OKLCH status palette, Pixel Blue for identity only, system font, Lucide. Every piece is shown light + dark. Forms follow the portal forms.md spec exactly.

Forms · 01

Field — anatomy & states

One <Field> renders label, optional hint, conditional error, the input, and an optional below line — in that fixed order. Error text sits above the input (so a screen reader hits it before the control), in the failed colour, normal weight, no icon.

Forms · 02

Password & the below async line

<PasswordInput> adds a Show / Hide toggle. The below line is reserved for live availability checks (token validation, provider detection): aria-live="polite", text-only, coloured by state. Hide it entirely when “available” adds nothing.

Forms · 03

FormSummary

A top-of-form panel with role="alert" so it’s announced on render. Lists client-validation errors; each links to the failing field’s id. Renders nothing when there are no errors.

Forms · 04

Inline banner — form-message

A message in document flow (not floating) at the top of a section or form. The server message ($message) always renders here, at the very top of the form — above FormSummary.

Forms · 05

Add a connection — every state on one form

The real add-connection form showing server banner + FormSummary + a field in error + a healthy async below together. Provider is auto-detected from the host — no provider picker.

Forms · 06

Submit buttons

A submit button is always pressable. Pressing an incomplete or invalid form is how a user invokes validation — errors render in the summary and inline, focus moves to the first one. We never disable submit until valid, and never grey it out waiting for input: a disabled button is a dead end with no explanation, and a user should never be left at one.

The only time it’s disabled is after it’s been pressed — while the submit is in flight — so a second click can’t fire. It shows a spinner and a “…” label, then resolves to a result (banner / toast / next screen).

Notifications · 07

Toasts

Corner-anchored, auto-dismissing. Anatomy: status icon + message + optional action + dismiss, with a coloured left edge. Three variants — success, error, info/neutral — on --shadow-lg. Enter/exit motion respects prefers-reduced-motion. (Try the dismiss / action buttons.)

Notifications · 08

Anchoring, stacking & the undo toast

Toasts anchor bottom-right on the options surface and stack newest-on-top. The undo toast is the destructive-action pattern — “Connection removed · Undo” — dismissing with a subtle fade (no countdown bar), ~5s lifetime.

Side panel · 09

Active-poll “live · 10s” indicator

While the side panel is open Pipes polls faster (10s vs the 1-min idle interval). A small pulsing dot + label communicates the live cadence without nagging.

Reference · 10

When to use what · new tokens

● Inline banner

The outcome of the thing in front of you — a submit result, a validation failure, a section-level state. Stays put, in flow, until resolved. Use for: add-connection success/failure, token-expired on a connection, “no repositories match”.

● Toast

A transient confirmation of an action that already succeeded, where the user’s attention has moved on. Auto-dismisses. Use for: settings saved, refresh triggered, and the undo pattern on delete. Never put a blocking error or required choice in a toast.

New tokens (everything else is reused)

Status, surfaces, shadows, radii all reuse v1. Notifications need just a couple of additions:

  • --toast-z — stack context above surface chrome. Suggest 2147483000 (extension overlay range).
  • --toast-gap — vertical offset between stacked toasts. 10px.
  • --toast-width — 320px (toast) · inset 16px from the anchored corner.
  • Elevation reuses --shadow-lg; left-edge accent reuses --success / --failed / --brand.

Token names: this doc’s CSS uses --p-* internally; the app’s names drop the prefix — --p-failed → --failed, --p-failed-bg → --failed-bg, --p-brand → --brand, etc. Build against the app’s tokens.
